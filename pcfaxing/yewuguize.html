DLC、Package、Bundle 状态与流转说明

用于统一资料审核、上架展示、价格销售和玩家权益之间的关系，避免把“审核通过”“上架”“可购买”当成同一状态。

DLC 管内容与展示Package 管价格与购买Bundle 组合 Package促销改变有效价格

1. 对象关系

四类对象各自负责一件事，状态相互校验但不互相替代。

内容对象DLC保存名称、介绍、图片、上架时间等展示资料；审核通过后才具备上架资格。
交易对象Package保存价格、区域价和包含的 App / Depot；销售中后才允许购买或免费领取并发放 License。
组合商品Bundle组合两个及以上 Package，保存独立展示资料和组合售卖价；自身审核与上架状态独立。
价格活动促销活动引用一个 Package，在有效时间内覆盖其成交价；不改变 DLC 资料和 Package 权益内容。

玩家侧看见详情、购买或领取、下载
↑ 覆盖有效价格

箭头表示引用或生效关系。DLC 与 Package 分别审核；Bundle、促销引用 Package，不复制其权益内容。
核心边界DLC 是否公开展示由 DLC 上架状态决定；是否可购买或免费领取由默认 Package 的销售状态决定；玩家是否拥有由 License 决定；能否下载由 Package 权益、Depot 与可用 Build 共同决定。

2. 状态定义

审核状态回答“内容是否获准”，业务状态回答“当前是否对玩家生效”。

对象审核状态业务状态决定什么不决定什么
DLC草稿／待审核／已通过／拒绝通过／已撤回待配置／待上架／预购中／已上架／已结束／已下架资料是否允许公开；DLC 是否在客户端公开展示价格、购买、License 和下载内容
Package草稿／待审核／已通过／拒绝通过／已撤回未上架／待上架／销售中／已结束／已下架价格及权益配置是否合规；是否已上架销售，能否购买或免费领取DLC 详情页资料是否公开展示
Bundle草稿／待审核／已通过／拒绝通过／已撤回未上架／待上架／已上架／已结束／已下架组合内容和售卖价是否合规；Bundle 是否展示并可购买成员 Package 的价格或销售状态
促销活动草稿／待审核／已通过／拒绝通过／已撤回未生效／待开始／进行中／已结束／已取消审核通过后，按活动时间决定折后价是否生效DLC 上架与 Package 权益内容
字段命名要求页面必须同时展示“审核状态”和对应的“上架状态／销售状态／活动状态”。审核已通过但尚未到开始时间时，业务状态叫“待上架”，不是“待通过”；“待通过”只表示运营尚未完成审核。

3. 核心生效条件

先明确玩家何时能够看到并购买 DLC，再阅读具体状态与操作规则。

DLC 资料已通过＋ DLC 已上架＋ 默认 Package 审核已通过＋ 默认 Package 销售中＋ 当前地区价格有效＋ 当前时间在开始与结束时间内＝ 展示购买／免费领取入口
执行顺序先审核内容和价格，再上架 Package 销售，最后按开始／结束时间自动上架和结束；手动立即上架只修改开始时间。任何前置条件不满足时，都应阻止操作并明确显示缺少的条件。

4. 状态切换与对应行为

每次状态变化必须由明确行为触发，并记录操作人、时间、对象、前后状态及原因。

4.1 通用审核状态

当前状态触发行为操作人目标状态系统行为
草稿提交审核开发者待审核校验必填项，生成不可变审核快照和审核记录；审核内容暂时锁定。
待审核审核通过平台运营已通过记录审核人和通过时间，开放后续上架或上架销售资格；不会自动上架或销售。
待审核拒绝通过平台运营拒绝通过审核说明必填；保留被拒快照，将提交内容回显到工作草稿供修改。
待审核撤回审核开发者已撤回终止当前审核，保留撤回记录，将提交内容恢复为可编辑工作草稿。
拒绝通过／已撤回修改后重新提交开发者待审核生成新的 revision_id 和审核快照；旧审核记录不覆盖。
已通过修改已生效资料开发者新修订草稿线上仍使用原已通过版本；新修订单独编辑、提交和审核，通过后替换线上版本。

4.2 DLC 上架状态

当前状态触发行为操作人目标状态系统行为
待配置DLC 资料通过，且默认 Package 审核通过并销售中系统校验待上架取得上架资格；继续等待计划时间，客户端仍不公开。
待上架开启预购且到达预购开始条件系统预购中展示 DLC 及预购入口；交易仍由默认 Package 完成。
待上架／预购中到达计划上架时间系统已上架重新校验资料、Package 销售状态和地区价格；通过后公开 DLC。
已上架到达结束时间系统已结束停止公开展示和新增购买；历史订单和License继续保留。
待上架／预购中立即上架开发者已上架开始时间改为当前时间，结束时间保持不变；结束时间已过或其他条件不满足时拒绝操作。
已上架／预购中下架开发者／平台运营已下架隐藏客户端入口，同步停售默认 Package，并取消未结束的关联促销。
已下架重新上架开发者待配置提交重新上架资料；重新校验审核结果、默认 Package、地区价格和计划时间。

4.3 Package 上架销售状态

当前状态触发行为操作人目标状态系统行为
未上架运营审核通过，开始时间在未来系统待上架保存已通过结果，等待开始时间；暂不允许购买或领取。
待上架到达开始时间系统销售中开放购买／领取和License发放。
未上架／待上架手动点击“立即上架”开发者销售中开始时间改为当前时间，结束时间保持不变。
销售中到达结束时间系统已结束停止新订单和新License；历史权益保留。
销售中下架销售开发者／平台运营已下架提前停止销售，并联动处理对应DLC、Bundle和促销。
已结束／已下架重新修改时间开发者待上架／销售中结束时间必须晚于当前时间，保存后按新时间重新计算状态。

4.4 促销活动状态

当前状态触发行为操作人目标状态系统行为
未生效促销审核通过平台运营待开始保存审核结果，等待开始时间，不提前改变成交价。
待开始到达开始时间系统进行中将折后价作为 Package 当前有效成交价。
进行中到达结束时间系统已结束停止折后价，恢复 Package 的非促销价格。
待开始／进行中取消活动开发者／平台运营已取消立即终止活动并恢复非促销价格，保留促销记录。
统一审计要求每次行为都记录 object_id、revision_id（涉及审核修订时）、行为名称、操作人、操作时间、原状态、目标状态和原因。系统自动行为的操作人记为“系统”。

9. Bundle 规则

Bundle 是独立组合商品，具有独立审核状态和上架／销售状态。

审核状态

草稿、待审核、已通过、拒绝通过、已撤回。审核组合资料、成员 Package 和组合售卖价；通过后只取得上架资格。

上架／销售状态

未上架、待上架、已上架、已结束、已下架。只有“已上架”时才向玩家展示并允许购买。

当前状态触发行为目标状态系统结果
未上架创建或修改开始／结束时间待上架保存时间范围；审核通过且未到开始时间时为待上架。
未上架／待上架手动点击“立即上架”已上架立即展示 Bundle 并开放购买；未操作时保持未上架或待上架。
待上架到达计划时间已上架所有成员 Package 均销售中时自动上架，否则保持待上架并提示阻断原因。
已上架到达结束时间已结束停止展示和新增购买，历史订单及权益保留。
已上架手动下架或成员 Package 失效已下架停止展示和新增购买，保留历史订单及已发权益。
已结束／已下架重新设置时间待上架／已上架重新设置开始和结束时间；也可立即上架，此时只把开始时间改为当前时间。
  • Bundle 不属于 Package；它只引用两个及以上 Package，并保存独立的展示资料和组合售卖价。
  • 创建和提交审核时只能选择审核已通过、销售中的 Package。
  • 任一成员 Package 下架销售，或对应 DLC 下架时，已上架 Bundle 自动下架。
  • 依赖恢复后 Bundle 不自动重新上架，需要再次确认上架方式。

10. 促销活动规则

促销属于价格活动，不设置“上架状态”。

审核状态

草稿、待审核、已通过、拒绝通过、已撤回。审核促销商品、折后价、时间和说明。

活动状态

未生效、待开始、进行中、已结束、已取消。审核通过后根据当前时间自动计算。

  • 促销必须绑定一个明确的销售对象。本期 Package 促销只影响该 Package 的直接购买价格。
  • Package 被某个 Bundle 引用时，Package 促销不会改变 Bundle 的组合售卖价、原价或折扣；Bundle 继续使用审核通过时保存的独立价格。
  • 只有销售中的 Package 才允许提交促销；折后价必须小于商品原价，商品原价只读。
  • 到达开始时间后自动应用折后价，到达结束时间后自动恢复 Package 的非促销价格。
  • 取消进行中的促销后立即恢复非促销价格，保留活动记录，不改变 Package 销售状态。
  • Package 下架销售或 DLC 下架时，未结束的相关促销自动取消。
  • 如后续需要 Bundle 促销，应单独创建以 Bundle ID 为目标的促销，不得复用成员 Package 的促销结果；本期暂不提供 Bundle 促销。

11. App、Depot、Build、Manifest 与 Release

采用完整 Build 模型：Build 聚合同一 App 下多个 Depot Manifest，并作为 QA、发布与回滚的原子版本。

最终口径Depot 是文件分区；Manifest 是单个 Depot 的不可变文件快照；Build 是一个 App 的完整版本；Release 是把完整 Build 发布到指定 Branch 的动作；Active Build 是该 App 在 Branch 当前生效的完整版本。

11.1 与 Steam 核心模型的对应关系

本平台对象关系说明
App → Depot1:N一个 App 可以按系统、架构、语言或内容用途拆分多个 Depot；一个 Depot 只归属一个 App。
Depot → Manifest1:N每次 Depot 上传成功生成一个不可变 Manifest；同一 Depot 可以保留多个历史文件版本。
Build → Depot Manifest1:N一个 Build 组合一个或多个 Depot Manifest，代表 App 在某一时刻的完整候选版本。
Release → BuildN:1一次 Release 发布一个完整 Build；同一 Build 可以按不同 Branch 或发布任务留下多条记录。
App + Branch → Active Build1:1每个 Branch 当前只指向一个完整 Build；切换一次即可原子更新整组 Depot Manifest。
与 Steam 的交互差异Steam 可通过一份 App Build 配置一次处理多个 Depot；本平台一期允许每个 Depot 分别创建 Upload Task 和运行 CLI，但所有任务必须属于同一个草稿 Build，完成后统一冻结。数据模型和最终版本语义保持一致。

创建 Build填写版本号和构建说明
→

→
CLI 分别上传每个任务扫描一个本地目录
→
生成 Manifest写入 Build 的 Depot 清单
→

CLI 边界CLI 命令仍只需要 Upload ID 与本地目录。Upload Task 在服务端保存 build_id、app_id 和 depot_id，因此多个单 Depot 上传结果可以稳定归入同一个 Build。

11.3 数据结构

Build

保存 build_id、app_id、版本号、构建说明、整体状态、创建时间和冻结时间。Build 是 QA、提包审核、Release 与回滚的业务对象。

BuildDepotManifest

保存 build_id、depot_id、manifest_id、是否必需、系统、架构和语言。唯一约束为 build_id + depot_id。

11.4 Build 状态与不可变规则

状态允许行为限制
草稿／上传中新增 Upload Task，添加、删除或替换 Depot Manifest不能提交 QA 或发布
待完成检查必需 Depot 是否齐全，执行“完成 Build”缺少必需 Depot 时不能完成
已冻结提交 QADepot Manifest 映射不可再修改
QA测试中／待提包审核记录平台子结论和整体结论任何文件变化都必须创建新 Build
已通过创建 ReleaseBuild、Manifest 和审核记录继续保持不可变

11.5 QA、Release 与 Active Build

  • 单个 Depot 上传阶段负责文件完整性、哈希、Manifest、架构和 SDK 文件静态检查。
  • QA 与提包审核以完整 Build 为对象，可以保存 Windows、macOS 等平台子结论，但最终结论属于 Build。
  • Release 保存 app_id、build_id、Branch、发布方式、计划时间、审核状态、执行状态和实际生效时间。
  • 创建、待审核、审核通过、取消或执行失败均不修改 Active Build。
  • 只有 Release 执行成功后，才原子更新 app_id + branch 对应的 active_build_id。

11.6 客户端下载

AppID + Branch→ Active Build→ BuildDepotManifest→ 按系统、架构、语言与 License 返回 Manifest

客户端始终从同一个 Build 解析所需 Manifest，不会出现 Windows、macOS 或语言资源来自不同版本的混合状态。

11.7 回滚

  • 回滚选择历史完整 Build，并创建新的回滚 Release。
  • 任务执行成功后，active_build_id 原子指向目标历史 Build。
  • 旧 Build、Manifest 与 Release 均不修改、不删除。
  • 记录操作人、原因、回滚前 Build、目标 Build、Branch、时间和结果。

11.8 DLC 边界

Base App Build

可以包含本体 Windows、macOS、公共资源和语言等属于 Base App 的 Depot Manifest。

DLC App Build

DLC 有独立 AppID，使用自己的 Depot、Build 与 Release，不将 DLC Depot 混入 Base App Build。

删除的旧口径不再使用“一 Build 只对应一个 Depot”“一 Build 只对应一个 Manifest”“按 Depot 分别维护 Active Build”或额外增加 AppVersion 的方案。最终统一为：一个完整 Build 聚合同一 App 下多个 Depot Manifest。
